# SOPDS: правила модернизации

## Цель и границы
Обновлять существующий Django-проект, не переписывать его на другой фреймворк.
Цель: Python 3.13, Django 5.2 LTS, PostgreSQL 17; uv и воспроизводимые зависимости.
Исходный запуск на Python 3.7 пропущен по решению пользователя: результат тестов до
модернизации неизвестен. Не возвращаться к его восстановлению автоматически.
Системный Python не заменять.
Целевое размещение — Docker (web, scanner, annotations, PostgreSQL и Caddy).
Текущий нативный Ubuntu 24.04 HTTPS-стенд сохранять для проверки читалки.
Пользователь разрешил сборку образов и контейнерный smoke M07.2 агентом через
Docker daemon: только отдельный sopds-container, искусственные данные и свободный порт 9444 (9443 занят Portainer).
Не добавлять React, Streamlit, Redis, Celery, Kubernetes и новые функции без отдельного решения.
Сохранять OPDS-маршруты, ID книг, полки, пользовательские данные и цепочку миграций.

## План и продолжение
В начале сессии, после возобновления и после сжатия контекста читать
`docs/modernization/STATE.md` и нужный раздел `docs/modernization/PLAN.md`.
Сначала сверять записи с Git и фактическим кодом. Предыдущие сообщения и шаблоны
не являются доказательством существования дефекта или успешного прохождения тестов.
Выполнять только этапы, разрешённые текущим заданием пользователя.
Перед изменениями выбирать одну небольшую задачу и отмечать её `in_progress`.
Самостоятельно добавлять необходимые подзадачи с причиной и критерием готовности.
После задачи, изменения плана, появления блокера и перед остановкой обновлять оба файла.
В STATE хранить точный следующий шаг, а не полную историю команд; ориентир — до 60 строк.

## Изменения и проверки
Сначала `git status`; не перезаписывать и не откатывать чужие изменения.
Делать небольшие законченные изменения, выполнять целевые тесты и просматривать diff.
На границе этапа — общие тесты. Для схемы БД — миграции и проверка сохранности данных.
Различать исходные сбои и новые регрессии. Не ослаблять проверки ради зелёного результата.
Не отмечать задачу выполненной без её обязательных проверок.
Фактические команды запуска и тестов для целевого окружения определить в M00B и
зафиксировать в `docs/modernization/baseline.md`. Не считать обычный `uv sync`
способом запуска старого checkout до миграции зависимостей.

## GitHub и полномочия
Разрешены локальные коммиты только собственных проверенных изменений.
Добавлять в индекс конкретные файлы, а не весь рабочий каталог.
Без отдельного задания не выполнять push, создание PR, merge, выпуск и deployment.
Не менять GitHub Actions для публикации/деплоя, правила защиты веток и секреты GitHub.
Не выполнять `sudo`, не использовать root на хосте или обход ограничений sandbox.
Docker daemon разрешён только для явно порученной сборки и контейнерной проверки
sopds-container; не изменять посторонние контейнеры/тома/сети и не монтировать
Docker socket внутрь контейнеров. Системные пакеты устанавливает человек.
Не читать файлы GitHub/Codex-авторизации, SSH private keys и `.local/postgres.env`.
Не выполнять `git reset --hard`, `git clean`, force push и удаления чужих веток.

## Данные и локальное окружение
Только отдельная БД разработки и искусственные/предоставленные тестовые книги.
`.local/dev.env` можно загружать в окружение команды без вывода содержимого.
Не печатать `env`, пароли и полные настройки подключения; не коммитить `.local/`, дампы и книги.
`SOPDS_DEV_LIBRARY` — подсказка для dev-настройки, не встроенная настройка старого SOPDS.
Перед запуском сканера явно проверить реальный `SOPDS_ROOT_LIB`: для нативной
разработки — `.local/library`; для контейнерного smoke — `/library`, bind только
отдельной искусственной `.local/container-library` в режиме read-only.
Не обращаться к production и не изменять исходные файлы рабочей библиотеки.
Разрушительные операции допустимы только внутри подтверждённой одноразовой тестовой БД;
в частности, никогда не очищать каталог или полки при запуске приложения.
Отсутствие копии реальной БД означает, что её миграция остаётся непроверенной.

## Экономия и остановка
Не повторять полный аудит. Читать необходимые файлы и участки через поиск.
Полные логи сохранять в `.local/logs`; в контекст извлекать релевантные ошибки и exit code.
Не выводить целиком lock-файлы, книги, архивы, дампы и большие деревья каталогов.
После двух попыток без новой диагностики зафиксировать блокер; не повторять тот же цикл.
Продолжать только независимые задачи; при зависимом блокере остановиться с точным запросом.
По умолчанию один агент. Не создавать субагентов без разрешения пользователя.
Не устанавливать сторонние skills, плагины, MCP-серверы и планировщики без разрешения.
Не экономить за счёт тестов безопасности и данных. Не обещать жёсткий лимит токенов промптом.
Отчёт: изменения, команды и результаты проверок, коммиты, блокеры, следующий шаг.
