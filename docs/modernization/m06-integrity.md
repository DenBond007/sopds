# M06.9 — полки и порядок выдачи

Дата: 2026-09-25. Выполнен разрешённый следующий шаг обзора M06.8:
уникальность полок и устойчивый порядок web/OPDS. Постоянное развёртывание,
push, изменение dev-БД и временного HTTPS probe в задачу не входят.

## Полки и миграция 0006

- До исправления две синхронизированные попытки скачивания создали две
  записи полки: тест получил `2 != 1`. Проверка ограничения БД также упала:
  `IntegrityError not raised`. Это воспроизведение на искусственных данных.
- `bookshelf_user_book_uniq` задаёт уникальность `(user, book)` на уровне БД.
  Существующий `get_or_create()` при конкуренции получает уже созданную запись.
  Перед добавлением ограничения миграция проверяет старые дубли и при их
  наличии останавливается; строки, ID и readtime автоматически не меняются.
- Конкурентные скачивания и повторный запрос возвращают HTTP 200 и точные
  байты книги, оставляют одну запись с прежними ID/readtime. Разные читатели
  по-прежнему имеют отдельные полки. Проверка цепочки 0001 → 0006 сохраняет
  пользователя, ID книги/полки/связей, время чтения и аннотацию.
- Адресная группа: 26/26 тестов, exit 0; тестовая БД удалена.

## Проверка восстановленного снимка

Канонический искусственный снимок M06.2
`.local/backups/m06-dev-canonical-20260924T112044Z.dump` восстановлен клиентом
PostgreSQL 17 в новую `sopds_m06_shelf_restore_20260925`. Перед созданием
проверены локальный тестовый сервер и отсутствие БД. В восстановленной
копии повторяющихся пар полки нет.

Миграция 0006 и обратная миграция на 0005 прошли. Сравнение количества и
хешей всех строк всех таблиц public подтвердило сохранность данных,
включая пользователей, полки, книги, связи, аннотации и настройки. Только
ожидаемая история django_migrations исключена из сравнения. Книги на диске
эта проверка не читала и не меняла; сканер не запускался.

Отклонение: первая очистка завершилась `ObjectInUse`, поскольку контекст
psycopg2 завершал транзакцию, но оставлял собственное соединение открытым.
Проверочный скрипт исправлен на явное закрытие. После завершения процесса
подтверждено отсутствие подключений и удалена только созданная здесь БД;
принудительное завершение чужих сеансов не применялось. Ошибка очистки не
затронула успешное сравнение прямой и обратной миграций.

## Порядок web/OPDS

- Добавлен ID как последний ключ сортировки книг, каталогов, авторов,
  серий, жанров и полок. Предыдущие приоритеты названий, дат и номеров серии
  сохранены. Общая арифметика пагинации не менялась.
- Повторы ID, вызванные несколькими связями авторов/жанров и общими авторами
  разных изданий, убраны из результата запроса. Записи связей не удаляются.
- Общий запрос книг серии возвращает книгу один раз. При конфликтующих
  старых номерах одной книги в выбранной серии для сортировки используется
  минимальный номер; номера других серий не влияют на порядок.
- До исправления 7 тестов дали 32 падения, включая повтор `[102,104,104,102]`
  на страницах полки вместо `[101,102,104,105]`. После исправления адресная
  группа 30/30 прошла. Проверены реальные ответы Django web/OPDS, одинаковые
  ключи, пересечение страниц каталогов/книг, старые связи, изоляция полок и
  сохранение представителя/счётчика скрытых изданий. Дополнительный сценарий
  OPDS «книги автора без серии» включён в общий прогон.

## Пределы проверки

Проверены искусственные данные новой установки. Это не доказательство
переноса прежней рабочей БД. Уникальность станет действовать на другом
стенде после применения 0006 к его БД в рамках отдельной задачи обновления
с предварительной проверкой копии. На dev и HTTPS probe миграция не применялась.
Устойчивый порядок не устраняет смещение OFFSET при добавлении/удалении
книг между запросами страниц. Реальная читалка, доверие CA на устройстве,
постоянный запуск и разрешённый удалённый CI остаются условиями M06.
