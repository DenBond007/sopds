# M06.13–M06.15: подготовка нативного запуска

## M06.13 — Gunicorn и конвертеры

2026-09-26: `infra/gunicorn.conf.py` задаёт два sync-worker, один поток,
loopback, приватную umask, timeout/graceful_timeout 330 с при пределе
конвертера 300 с. Оба пути конвертации теперь останавливают и дожидаются
группы процесса также при SystemExit рабочего процесса. SIGKILL не позволяет
выполнить Python-cleanup; для сервисов требуется KillMode=control-group.

Реальные тесты Gunicorn/Django на новой одноразовой PostgreSQL test-БД:
конвертация 32 с и отдельный каталог (<5 с), скачивание 8 МиБ с задержкой
и проверкой SHA-256 плюс каталог, SIGABRT рабочего процесса (нет конвертера
и рабочих файлов), SIGTERM master (запрос завершается, файлы удалены).
Отдельная регрессия подтверждает остановку дочернего процесса конвертера.
Существующие тесты покрывают срабатывание предела и ошибки HTML-конвертера.

Адресный набор: 16/16 за 44.110 с; общий: 179/179 за 83.466 с, exit 0.
Использован `.local/run-m06-integrity-tests.sh`: dev-назначение сверено,
PostgreSQL 17 подтверждён, заранее отсутствующая test-БД создана и удалена
Django. `manage.py check`, `makemigrations --check --dry-run`,
`gunicorn --check-config --config infra/gunicorn.conf.py sopds.wsgi:application`
и `git diff --check` прошли. Логи: `.local/logs/m06-gunicorn-*.log`.
Схема не менялась; параметры являются проверенной исходной конфигурацией
для двух одновременных запросов, а не результатом нагрузочного подбора
для произвольного числа клиентов.

## M06.14 — сканер и шаблоны служб

`manage.py sopds_scanner run` работает в foreground, пишет в stderr/journal,
не создаёт PID/log-файлы. SIGTERM/SIGINT останавливают планировщик с ожиданием
текущего scan; расписание и advisory lock сохранены. Legacy start/stop/restart
используют закрытый flock PID-файл с временем старта и Linux pidfd; старые
числовые PID-файлы отклоняются без сигнала. При stop >30 с restart не начинает
новый процесс, а сообщает, что прежний ещё завершает scan. Daemon umask — 077.

33/33 адресных теста за 11.448 с, exit 0: два цикла start/SIGTERM во время
scan сохраняют ID, readtime и полку; чужой/старый PID не получает сигнал,
блокировка и очистка PID-файла работают. Существующие тесты scan/worker прошли.
`systemd-analyze --user verify` трёх шаблонов — exit 0, замечаний нет.
Логи: `.local/logs/m06-scanner-targeted.log`, `m06-systemd-verify.log`.

Шаблоны `infra/systemd/*.service.example` рассчитаны на пользовательские
службы; перед установкой оператор корректирует WorkingDirectory/ExecStart
и готовит приватный `%h/.config/sopds/service.env`. Обязательны DB-переменные,
SOPDS_SECRET_KEY и TIME_ZONE; web также требует SOPDS_PRIVATE_HOST и
SOPDS_STATIC_ROOT. Перед scanner проверить SOPDS_ROOT_LIB; для разработки
использовать `.local/library`, в HTTPS probe только его подтверждённую копию.
Все службы используют UMask=0077, KillMode=control-group и journal.
TimeoutStopSec scanner=300 с: до постоянного запуска измерить полный scan
и при необходимости увеличить время; при принудительном убийстве ждать
штатного завершения нельзя. Worker=45 с, web=345 с.

Постоянная установка, user linger/старт до входа пользователя и реальная
перезагрузка машины не выполнялись; это отдельные операторские проверки.
