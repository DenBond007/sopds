# M08: личная библиотека и эксплуатация

Дата: 2026-10-18. Исходный HEAD: `b21543e`. Разрешение пользователя: выполнить все
рекомендации анализа. Только отдельные тестовые БД и искусственная библиотека;
нативный HTTPS probe на 8443 и посторонние контейнеры сохраняются.

## Пользовательские изменения

- Поиск: совместные фильтры названия, автора, серии, жанра, языка и формата.
  Дополнительные параметры одинаково применяются к HTML и OPDS; старые пути и ID
  сохранены. Пагинация сохраняет фильтры, `&`, `+`, `%`, `#` и Unicode.
- Личные списки «Хочу прочитать», «Читаю», «Прочитано» доступны после входа.
  Они независимы от прежней полки скачиваний. Изменения требуют POST и CSRF;
  фильтрация и позиция всегда принадлежат текущему пользователю.
- FB2-читалка восстанавливает относительную позицию прокрутки с сервера.
  Скрипт выполняется в доверенной внешней странице; iframe книги не может
  выполнять скрипты, формы, popups или top-navigation. Старый preview сохраняет
  исходный строгий sandbox. EPUB/MOBI/PDF/DJVU доступны для скачивания;
  встроенное чтение этих форматов не добавлено.
- Ссылка на дубликаты теперь содержит настоящий ID книги.
- Basic Auth подтверждает только текущий OPDS-запрос: не создаёт browser session
  и не обновляет last_login. Обычные web-сессии сохранены.

## Схема и данные

Миграция `0007_reading_and_service_status` добавляет ReadingState и ServiceStatus.
Существующие Book, bookshelf, настройки и связи не изменяются. Пара
пользователь–книга уникальна, позиция ограничена 0..10000 на уровне БД.
Новые модели также создают два Django content types и восемь permissions.
Восстановление при откате выполняется из matching backup; обратная миграция
удаляет новые списки/позиции, поэтому не применяется к единственной рабочей БД.

## Диагностика

Страница `/web/operations/` доступна только staff. Она показывает scanner/worker,
последний успешный scan, ошибки и возраст очереди, истёкшие leases, свободный диск
приложения и последнюю проверенную резервную копию. Секреты не выводятся.

```sh
# После безопасной загрузки переменных отдельного окружения:
.venv/bin/python manage.py sopds_health
# Пороги можно согласовать с реальным расписанием и объёмом библиотеки:
.venv/bin/python manage.py sopds_health --max-scan-age-hours 840 \
  --max-heartbeat-age-seconds 1200 --max-queue-age-seconds 900 --max-backup-age-hours 48
```

Команда возвращает JSON и ненулевой exit при проблемах. Порог scan по умолчанию
35 дней учитывает сохранённое месячное расписание. Heartbeat scanner идёт раз в
10 минут, worker — не реже 30 секунд в активном цикле. Ошибки сканирования не
маскируются heartbeat. HTTP healthcheck не заменяет эту проверку. Автоматические
сообщения во внешние сервисы не настроены; результат и сбои видны в UI/journal.

## Резервирование и регулярное обслуживание

```sh
python3 scripts/ops/maintenance.py --env-file .local/container.env \
  --backup-dir .local/backups --retain 7 --amd64
python3 scripts/ops/install-cron.py --env-file .local/container.env \
  --backup-dir .local/backups --amd64
# Расписание проверяет только собственный блок, остальные задания не меняет.
tail -n 30 .local/logs/maintenance-schedule.log
```

Скрипт работает только с Compose-проектом `sopds-container`. В окне резервирования
он останавливает web/scanner/annotations/Caddy, дожидаясь активных операций, сохраняет
БД, библиотеку, Caddy data/CA и закрытую конфигурацию; manifest хранит Git commit, фактические app/Caddy image ID и fingerprint uv.lock. PostgreSQL не останавливается. Caddy также приостановлен на snapshot, чтобы renewal сертификата/ключа не пересекался с архивированием; отдельный tar-контейнер читает тот же том. Дамп восстанавливается в новую одноразовую БД, и fingerprints
всех public-таблиц сравниваются с исходником. Временная БД удаляется, ранее
работавшие службы запускаются даже при ошибке. Затем очищаются истёкшие сессии.
Успешный manifest создаётся после восстановления; незавершённые снимки и чужие
каталоги ротация не удаляет. По умолчанию остаются семь успешных снимков.

Установлен собственный блок user crontab. Существующие задания сохранены.
Каждые 15 минут лёгкий wrapper проверяет московское время; один полный backup
выполняется после 03:30 Europe/Moscow. Уже проверенный полный snapshot за сегодня
предотвращает повтор; пропущенное время догоняется после включения машины.
Параллельные ручные и плановые backup закрыты общим flock, после ошибки следующая попытка не раньше часа.
Остальные пробуждения тихие; вывод попыток идёт в закрытый локальный журнал.

На хосте cron/docker active, Linger=no. Этот вариант не зависит от user manager
и не меняет системную политику logout. Шаблоны systemd и install-user-timer.py
сохранены как альтернатива для окружения с подходящей политикой user manager;
одновременно два расписания включать не нужно. Полная перезагрузка общего хоста
в этой задаче не выполняется.

Окно резервирования временно делает web недоступным. Библиотека должна оставаться
неизменной внешними программами до окончания snapshot. Полный snapshot копирует
книги; для очень большой библиотеки нужно согласовать частоту и свободное место.
`--database-only` явно исключает книги и отражается в scope manifest. Это не
полная замена независимой копии файлов библиотеки.

Backup и runtime.env закрыты 0700/0600; не коммитить и не публиковать. В приложение
монтируется только отдельная сводка `.local/backup-status/latest.json` без секретов,
а не сами резервные копии. Перед первым up каталог сводки должен существовать:

```sh
mkdir -p .local/backup-status
chmod 755 .local/backup-status
```

При изменении host-пути укажите `SOPDS_BACKUP_STATUS_DIR` и `--status-dir` одинаково.

## Производительность

На новой одноразовой PostgreSQL 17.11: 100000 синтетических книг, 7 повторов:

| Сценарий | Медиана, мс | p95, мс |
|---|---:|---:|
| Выбор через OFFSET 75000 | 14.576 | 15.782 |
| Выбор через индексный порог PK | 0.626 | 0.915 |
| Поиск подстроки с сортировкой | 14.889 | 15.278 |

Для 300 дубликатов число SQL уменьшилось с 301 до 4. Обход идёт пакетами по 128,
без загрузки всей группы и без двух запросов на каждую книгу. Выбор случайной
рекомендации использует индексный порог вместо OFFSET; при разрывах ID это не
равномерная выборка по всем книгам. Индексы поиска вслепую не добавлялись:
на этом объёме измеренный поиск занимал около 15 мс. На реальной библиотеке
показатели могут отличаться.

```sh
# Только НОВАЯ ПУСТАЯ одноразовая БД с префиксом sopds_bench_ после migrate:
DB_NAME=sopds_bench_example .venv/bin/python manage.py sopds_benchmark \
  --confirm-disposable-db sopds_bench_example --books 100000 --repeats 7
```

Вставки всегда откатываются транзакцией; планы EXPLAIN ANALYZE входят в JSON.
Создание/удаление самой test-БД делает оператор. Результат этого запуска и планы:
`.local/logs/m08-benchmark.json`; созданная БД удалена.

## Проверки и внешние ограничения

Адресные проверки ссылок/auth, функций/SQL/миграций и Chromium/сканера пройдены.
Полный локальный набор: 200/200 за 85.315 с с Chromium. Дополнительные два теста расписания и тест retention прошли отдельно. Итоговые Docker/HTTPS, backup и CI записываются в STATE/PLAN. Прежний удалённый CI для `daa2ab5` подтверждён как
failure; это не результат нового кода.

Нельзя подтвердить автоматически: конкретную физическую читалку и её доверие CA,
а также запуск всей машины после reboot. Перезагрузка общего хоста не выполняется.
ARM64 не проверен. При фактической проверке временные нативные user units не найдены, порт 8443 закрыт. Файлы и искусственные данные probe сохранены без изменений. Для читалки доступен обновлённый Docker HTTPS на 9444; его CA — `.local/m07/root.crt`.

При включении Docker после трёхнедельной остановки обнаружен просроченный leaf
сертификат: очистка Caddy пересеклась с его renewal. После штатного restart Caddy
сертификат выдан повторно прежним CA; TLS healthcheck и HTTPS smoke прошли.
Корневой CA, ключи и тома не удалялись. Перед чтением после долгого простоя
проверять health Caddy; при таком же сообщении missing key после storage cleanup
достаточен restart именно Caddy с последующим TLS healthcheck.
